## 1. Data Structure Implementation: Custom Min/Max Priority Queue Heap

### 1.1 Overview & Design Decisions
The `PriorityQueueHeap<T>` is a generic, array-based binary heap implemented from scratch without using Java's built-in `java.util.PriorityQueue`. 
- **Underlying Storage**: Dynamic Object array (`Object[] data`) with automated capacity expansion ($2\times$ growth factor).
- **Ordering Flexibility**: Supports custom ordering via a `Comparator<? super T>`. When no comparator is provided, it defaults to natural ordering (`Comparable<T>`).
- **Heap Invariant**: Parent index $P = \lfloor (i - 1) / 2 \rfloor$. Left child $L = 2i + 1$, Right child $R = 2i + 2$. The top element (`data[0]`) always holds the highest-priority element according to `compare(a, b) < 0`.

### 1.2 Key Operations & Complexity
- **`insert(T value)`**: Appends element at index `size` and performs `siftUp(size)`. Time Complexity: $O(\log N)$ worst/average case, $O(1)$ best case.
- **`extractTop()`**: Replaces root with last element `data[size-1]` and performs `siftDown(0)`. Time Complexity: $O(\log N)$.
- **`peek()`**: Returns `data[0]` in $O(1)$ time.
- **`heapify(T[] items)`**: Builds heap in-place by calling `siftDown()` on non-leaf nodes starting from index $\lfloor N/2 \rfloor - 1$ down to $0$. Time Complexity: $O(N)$ linear time.

## 2. Algorithm Implementation: Greedy Priority-Based Resource Assignment

### 2.1 Problem Description & Localisation
In Ghanaian municipal sanitation operations (e.g., Osu, Madina, Adenta, Tema), waste collection requests arrive continuously with varying urgency levels (1 = Low to 5 = Critical) and estimated truck-hours required. Collection trucks (`Resource`) operate from base depots across local coordinate grids.

### 2.2 Algorithmic Strategy
The `GreedyAssignment` algorithm resolves resource allocation by making locally optimal choices at each decision step:
1. All pending `ServiceRequest` objects are inserted into a `PriorityQueueHeap<ServiceRequest>` parameterized with a Max-Urgency comparator:
   $$\text{Comparator}(A, B) \Rightarrow \text{Primary: } B.\text{urgency} - A.\text{urgency}, \quad \text{Secondary: } A.\text{cost} - B.\text{cost}$$
2. In each iteration, `extractTop()` retrieves the highest-urgency request in $O(\log N)$ time.
3. The algorithm scans available trucks in $O(M)$ time to assign the nearest truck by Euclidean distance $d = \sqrt{(x_1 - x_2)^2 + (y_1 - y_2)^2}$.
4. The assigned truck is marked unavailable (`available = false`), and a step log entry is recorded in the dispatch trace.

## 4. Counterexample: Where Greedy Fails (Section 10 Requirement)

### 4.1 Theoretical Context
The simple Greedy rule (*"always serve highest urgency next"*) is optimal for unconstrained single-job dispatching. However, under a **hard budget constraint** (e.g., maximum daily truck-hours), the greedy choice property breaks down.

### 4.2 Concrete Counterexample Data
- **Truck Budget**: 6 truck-hours
- **Pending Requests**:
  - $R_1$: Urgency = 5 (Critical), Cost = 6 hours
  - $R_2$: Urgency = 3 (Medium), Cost = 3 hours
  - $R_3$: Urgency = 3 (Medium), Cost = 3 hours

### 4.3 Execution Comparison
- **Greedy Strategy**: Sorts by urgency descending ($R_1 \to R_2 \to R_3$).
  - Picks $R_1$ (Urgency 5, Cost 6h). Remaining budget = 0h.
  - **Total Urgency Served = 5**.
- **Optimal Strategy (0/1 Knapsack Solution)**:
  - Selects $R_2 + R_3$ (Cost 3h + 3h = 6h).
  - **Total Urgency Served = 3 + 3 = 6**.

### 4.4 Conclusion & Handoff
Greedy achieves $5$, whereas Optimal achieves $6$. Thus, Greedy is **suboptimal under hard budget constraints**. This establishes the documented handoff to the **Dynamic Programming (0/1 Knapsack)** module.

## 6. Oral Defense Summary & Key Takeaways

- **Data Structure Choice**: Custom Binary Max/Min Heap (`PriorityQueueHeap`) providing $O(\log N)$ extraction vs $O(N)$ linear array scan.
- **Time Complexity**: $O(N \log N + N \cdot M)$ overall dispatch execution time.
- **Counterexample**: Proved greedy fails under knapsack budget constraints.
